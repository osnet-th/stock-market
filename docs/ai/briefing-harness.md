# Briefing Harness

이 문서는 plan만으로 구현 의도가 와닿지 않는 문제를 줄이기 위해, 코드 기준 브리핑을 언제 어떤 깊이로 수행할지 정의한다. 상세 구현 설명은 필요한 만큼만 제공하고, 구현 생산성을 해치지 않도록 큰 결정 지점에서 짧게 멈추는 것을 기본으로 한다. 최상위 계약은 [agent-harness.md](agent-harness.md)이며, 충돌 시 더 보수적인 규칙을 따른다.

---

## 목적

- 요구사항을 현재 코드 흐름에 대입해 plan 승인 전 이해도를 높인다.
- plan 작업 항목이 실제 코드의 어느 계층과 파일에 대응되는지 명확히 한다.
- 구현 중 큰 단위가 끝날 때 변경 흐름과 다음 작업을 짧게 확인한다.
- 최종 검증 전에는 구현 이해 확인 Gate(`explain` 단계)로 전체 구조와 요구사항 커버리지를 확인하고 GAP 결정을 받는다.

---

## 적용 대상

아래 중 하나에 해당하면 이 하네스를 적용한다.

- issue 기반 Plan 또는 Implementation 작업
- public API, Entity, DB schema, 권한, 스케줄러/배치/외부 API 연동 흐름 변경
- 사용자가 코드 맥락 설명, 실행 브리핑, plan-to-code 매핑, 작업 단위 브리핑을 요청한 경우
- plan만으로 영향 범위 파악이 어려운 작업

단순 Question, 코드 읽기, 작은 문서 수정, 명백한 오타 수정에는 생략할 수 있다. 생략 시 이유를 짧게 말한다.

---

## 브리핑 단계

### 1. 현재 코드 기준 실행 브리핑

plan 작성 또는 최종 승인 전에 수행한다. 요구사항을 현재 코드 흐름에 대입해 설명한다.

포함 항목:

- 현재 처리 흐름
- 변경 후 처리 흐름
- 새로 생길 진입점
- 건드리는 테이블/컬럼 또는 외부 연동
- 기존 기능 영향
- 큰 리스크와 확인 필요 사항

템플릿:

```text
현재 흐름:
변경 후 흐름:
새 진입점:
주요 저장 구조:
기존 기능 영향:
리스크/확인 필요:
```

### 2. Plan-To-Code 매핑 브리핑

plan 작성/수정 후 승인 전에 수행한다. plan의 작업 항목이 실제 코드 어디에 붙는지 짧게 매핑한다.

포함 항목:

- plan 작업 항목별 주요 클래스/파일
- 새 파일과 확장 파일의 역할
- blocked path 또는 건드리지 않을 기존 기능
- 테스트 대상과 제외 대상의 이유

템플릿:

```text
plan 작업 1 -> 코드 위치/책임:
plan 작업 2 -> 코드 위치/책임:
수정하지 않는 영역:
테스트로 확인할 영역:
```

### 3. 작업 단위별 체크포인트 브리핑

구현 중 큰 작업 단위가 끝났을 때 수행한다. 모든 작은 변경마다 멈추지 않고, plan 또는 대화에서 합의한 체크포인트에서만 멈춘다.

기본 체크포인트 예:

- 스키마/Entity/Model 변경 후
- 핵심 use case/service 구현 후
- 조회/필터/정렬 또는 권한 조건 연결 후
- API 요청/응답 계약 연결 후
- 단위테스트 작성/통과 후

템플릿:

```text
이번에 바뀐 흐름:
주요 변경 파일:
직전 가드 리뷰 결과:
기존 기능 영향:
다음 작업:
남은 위험/확인 필요:
```

### 3-1. 체크포인트 범위·방향 가드

체크포인트 브리핑 진입 시 직전 큰 작업 단위의 변경분이 요구사항 방향과 root plan 범위를 지키는지 검사한다. 이 가드는 `/ce:review` 등 공식 리뷰 단계를 대체하지 않는다.

절차:

1. **diff 스냅샷 고정 + 경로 검사(메인, 즉시)**: `/Users/thlee/Documents/personal/stock-market/scripts/checkpoint-guard.sh {worktree경로}`를 실행한다. 스크립트가 신규 파일 포함 스냅샷을 `.claude/issues/{이슈번호}/checkpoints/task-{N}.diff`로 저장하고, 변경 파일을 root plan의 `allowed_paths`/`blocked_paths`와 대조한다.
2. **위반 처리**: 스크립트가 exit 1(경로 위반)이면 서브에이전트를 스폰하지 않고 즉시 중단해 태형님에게 보고한다. exit 2(plan 미발견)이면 plan 상태를 먼저 확인한다.
3. **의미 검사(서브에이전트, 백그라운드)**: read-only 리뷰 서브에이전트를 백그라운드로 스폰하고, 메인은 기다리지 않고 다음 작업 단위를 진행한다. 서브에이전트는 파일을 수정하지 않고 판정만 반환한다.
   - 입력: ①이번 스냅샷 `task-{N}.diff`, ②직전 스냅샷 `task-{N-1}.diff`(있는 경우, 이번 단위 변경분 식별용), ③root plan 문서, ④Harness Brainstorm 문서, ⑤`.claude/issues/{이슈번호}/{이슈번호}.md`, ⑥이번 변경분이 plan 작업 리스트의 어느 항목에 대응하는지

판정 분류(판정마다 근거를 `파일:라인`으로 포함한다):

| 판정 | 의미 |
|---|---|
| SCOPE_CREEP | plan에 없는 파일·기능·리팩토링이 변경분에 포함됨 |
| DIRECTION_DRIFT | plan 항목 안이지만 이슈/브레인스톰에서 확정한 요구·정책과 다른 방향으로 구현됨 |
| PLAN_UPDATE_NEEDED | plan대로 구현이 불가한 정황이 확인됨 |
| CLEAN | 이상 없음 |

판정별 처리:

- **SCOPE_CREEP**: 결과 수신 즉시 현재 작업을 중단하고 태형님에게 보고한다. 다음 체크포인트까지 미루지 않는다.
- **DIRECTION_DRIFT, PLAN_UPDATE_NEEDED**: 다음 체크포인트 브리핑에서 보고하고 태형님 판단을 받는다. 임의 수정하지 않는다. plan 갱신이 필요하면 plan 갱신·재승인 절차로 전환한다.
- **CLEAN**: 다음 체크포인트 브리핑의 "직전 가드 리뷰 결과" 항목에 한 줄로 기록한다.
- 마지막 작업 단위의 가드 결과는 다음 체크포인트가 없으므로 리뷰 단계 진입 전에 회수해 보고한다.

### 4. 전체 구현 이해 확인 Gate

구현 완료, 리뷰/수정 이후, 검증 선택 전에는 `explain` 단계에서 `check-implementation-explainer` 스킬의 설명 구조를 따른다. 이 단계는 중간 체크포인트보다 넓게 전체 처리 흐름, 계층별 역할, 도메인 정책/조회 규칙, 데이터 저장 구조, 권한/예외/트랜잭션, 유지보수 포인트, 잔여 위험, 그리고 root plan `## 요구사항 원장` 기준 요구사항 커버리지를 설명한다. 설명 후 커버리지 집계를 제시하고, `미충족`이 없고 `범위 제외`·`부분 충족`에 대한 태형님 GAP 결정이 끝난 경우에만 Gate를 완료한다.

---

## 운영 원칙

- 브리핑은 코드 나열이 아니라 요청이 시스템 안에서 어떻게 흐르는지 설명한다.
- 실행 브리핑과 plan-to-code 매핑은 길게 쓰지 않고, 태형님이 plan을 읽을 수 있는 코드 맥락을 제공하는 데 집중한다.
- 작업 단위별 체크포인트는 구현 생산성을 위해 큰 결정 지점에만 둔다.
- 체크포인트가 너무 잦아질 경우 태형님에게 묻고 병합한다.
- plan 범위 밖 변경이 필요해지면 브리핑이 아니라 plan 갱신과 재승인 절차로 전환한다.
- 이슈 코멘트, PR 설명에는 내부 작업용 md 파일 경로를 쓰지 않는다.

---

## Stop Gates

아래 조건이면 멈추고 태형님 확인을 받는다.

- issue 기반 Plan 또는 Implementation에서 실행 브리핑 없이 plan 승인 또는 구현으로 넘어가려 함.
- plan-to-code 매핑 없이 복잡한 plan 승인을 요청하려 함.
- 합의된 체크포인트에서 브리핑과 태형님 확인 없이 다음 큰 작업 단위로 넘어가려 함.
- 체크포인트 가드에서 경로 위반 또는 SCOPE_CREEP 판정을 받고도 중단·보고 없이 작업을 계속하려 함.
- 브리핑 도중 plan 범위 밖 파일, API, Entity, DB schema, 권한 정책 변경 필요가 확인됨.
- 최종 구현 이해 확인 Gate 없이, 요구사항 커버리지를 제시하지 않았거나, `미충족`이 남았거나, GAP 결정을 받지 않았는데 검증 선택, PR, 병합 단계로 넘어가려 함.
