# Test Planning Harness

이 문서는 단위 테스트 계획을 사용자와 합의하고, 승인된 계획에 따라 테스트 우선 구현을 진행하기 위한 공통 하네스다. 최상위 계약은 [agent-harness.md](agent-harness.md)이며, 충돌 시 더 보수적인 규칙을 따른다.

---

## 목적

- 테스트 의도와 기대 결과를 plan 단계에서 명확히 한다.
- 사용자는 테스트 코드 세부 구현이 아니라 Given / When / Then, 예외 케이스, 기대 결과를 확인한다.
- 단위 테스트를 작성하기로 한 작업은 `/ce:work` 진입 전에 테스트 시나리오 사용자 승인을 완료한다.
- work 단계에서는 승인된 테스트 계획에 따라 테스트 작성 → 실패 확인 → 운영 코드 구현 → 테스트 통과 확인 순서로 진행한다.

---

## 기본 원칙

- 테스트 코드는 명시적 요청 또는 승인된 plan의 단위 테스트 계획에 포함된 경우에만 작성한다.
- 테스트 계획은 plan 단계에서 사용자 확인을 받는다.
- 기능 구현 계획이 끝나기 전 또는 테스트 작성 여부가 확정되기 전에는 plan에 상세 테스트 케이스를 선기입하지 않는다.
- `test_plan_status: pending` 상태의 plan에는 테스트 작성 여부 확인 필요, 시나리오 미승인, 승인 후 반영 예정 같은 상태만 남기고 Given / When / Then 표나 구체 테스트 케이스 목록을 작성하지 않는다.
- `test_plan_status: approved`는 테스트 작성 여부만 승인된 상태가 아니라 Given / When / Then, 정상/예외 케이스, Mock 대상, 제외 범위, 검증 명령이 승인된 상태를 뜻한다.
- 단위 테스트를 작성하기로 했지만 테스트 시나리오가 `pending`이면 `/ce:work`로 구현을 시작하지 않는다.
- 단위 테스트 작성으로 결정되면 에이전트는 먼저 대화로 테스트 시나리오를 설명하고 태형님과 조정한 뒤, 승인된 시나리오만 plan에 기입한다.
- 단위테스트만 작성한다.
- 통합테스트와 E2E 테스트는 작성하지 않는다.
- Controller, JPA, Spring slice 테스트는 기본 제외한다.
- 외부 DB, 외부 API, Repository 등 외부 의존성은 mock 처리한다.
- 테스트는 상태 기반 검증을 우선한다.
- 메서드 호출 여부 검증은 작성하지 않는 것을 기본으로 한다.
- Given / When / Then 스타일을 권장한다.

---

## 테스트 범위

기본 테스트 범위는 단위 테스트로 제한한다.

우선 테스트 대상:

- domain model / domain service 정책
- application service 유스케이스 흐름
- mapper / adapter의 순수 변환 로직
- 예외 조건과 상태 변화

기본 제외 대상:

- Controller 테스트
- JPA 테스트
- Spring slice 테스트
- 통합 테스트
- E2E 테스트

기본 제외 대상은 아래 조건에 해당할 때만 별도 plan에 범위, 환경, fixture, 검증 명령을 명시하고 사용자 승인을 받은 뒤 진행한다.

- Controller에서 복잡한 request parsing, validation, response contract를 직접 다룸
- 인증/인가 또는 커스텀 예외 응답 포맷이 변경됨
- Repository 쿼리(QueryDSL 포함) 자체가 핵심 요구사항이고 SQL 회귀 위험이 큼
- DB schema 변경이 포함됨

## 문서 분리 규칙

기능별 테스트 계획은 plan 본문에 길게 작성하지 않고 별도 문서로 분리할 수 있다.

권장 경로:

```text
docs/plans/tests/{YYYY-MM-DD}-{issue-or-tbd}-{descriptive-name}-test-plan.md
```

plan 본문에는 아래 정보만 남긴다.

테스트 작성 여부 또는 시나리오 승인이 아직 확정되지 않은 경우:

```markdown
## 단위 테스트 계획
- 테스트 작성: 확인 필요
- 테스트 시나리오: 미작성
- 사용자 승인: 미승인
- 다음 단계: 기능 계획 승인 후 테스트 작성 여부를 확인하고, 작성하기로 하면 대화로 시나리오를 합의한 뒤 plan에 반영
```

테스트 시나리오가 승인된 경우:

```markdown
## 단위 테스트 계획
- 테스트 작성: 작성함
- 테스트 계획 문서: [테스트 계획](./tests/{test-plan-file}.md)
- 사용자 승인: 테스트 시나리오 승인됨
- 승인된 테스트 시나리오: 정상 N건, 예외 N건
- 검증 명령: `./gradlew test --tests "...TestClassName"`
```

테스트 계획 문서도 plan의 구현 승인 범위에 포함되므로, 해당 경로는 plan의 `allowed_paths`에 명시한다.

## Plan 단계

- 테스트 작성 여부를 결정한다.
- 기능 구현 계획을 먼저 정리하고, 단위 테스트 작성 여부가 확정되기 전에는 상세 테스트 시나리오를 plan에 기입하지 않는다.
- 단위 테스트를 작성하기로 했으면 에이전트가 대화로 테스트 시나리오를 설명하고 태형님과 조정한다.
- 단위 테스트를 작성하기로 했으면 `/ce:work` 전에 테스트 시나리오를 작성하고 사용자 승인을 받는다.
- 승인된 테스트 시나리오만 plan 본문 또는 테스트 계획 문서에 반영한다.
- 테스트 파일 경로와 테스트 계획 문서 경로를 `allowed_paths`에 포함한다.
- 테스트 대상 유스케이스를 명시한다.
- 핵심 Given / When / Then을 명시한다.
- 예외 케이스와 기대 결과를 명시한다.
- mock 대상과 제외 범위를 명시한다.
- 실행할 Gradle test task를 명시한다.

---

## Work 단계

1. 승인된 active plan을 확인한다.
2. 단위 테스트를 작성하기로 한 작업이면 테스트 시나리오가 사용자 승인되었고 `test_plan_status: approved`인지 확인한다.
3. 테스트 파일 경로와 테스트 계획 문서 경로가 `allowed_paths`에 포함되어 있는지 확인한다.
4. 승인된 테스트 시나리오에 해당하는 단위 테스트를 먼저 작성한다.
5. 단위 테스트 실패를 확인한다.
6. 운영 코드를 최소 범위로 구현한다.
7. 단위 테스트 통과를 확인한다.
8. 필요한 빌드 검증을 실행한다.
9. plan 체크리스트를 실제 완료 상태에 맞게 갱신한다.

---

## Stop Gates

아래 조건 중 하나라도 해당하면 즉시 중단하고 사용자 확인을 요청한다.

- 승인된 단위 테스트 계획 없이 테스트 파일 생성/수정이 필요함
- 테스트 작성 여부가 확정되지 않았거나 사용자 승인 전인데 plan에 상세 테스트 케이스, Given / When / Then 표, 구체 예외/클래스 중심 테스트 시나리오를 기입해야 함
- 단위 테스트를 작성하기로 했지만 테스트 시나리오가 사용자 승인되지 않은 상태로 `/ce:work` 진입이 필요함
- `test_plan_status: approved`인데 Given / When / Then, 예외 케이스, 기대 결과, Mock 대상, 검증 명령이 명시되지 않음
- plan에 없는 테스트 파일 생성/수정이 필요함
- 승인된 테스트 케이스와 다른 테스트 추가가 필요함
- 통합테스트/E2E 또는 외부 의존성 실사용이 필요함
- 테스트 실패 원인이 현재 plan 범위 밖 운영 코드 변경을 요구함
- 테스트 계획과 다른 public API, Entity, 구조 변경이 필요함
