# Git And PR Gate

이 문서는 Git, Pull Request, Merge, Final Cleanup 상세 규칙이다. 최상위 계약은 [agent-harness.md](../agent-harness.md)이며, 충돌 시 더 보수적인 규칙을 따른다.

---

## Git Harness

- 코드 구현 작업은 issue 브랜치 또는 issue worktree에서만 진행한다.
- `main` 또는 `master` 브랜치에서 코드 수정, 커밋, push를 하지 않는다.
- issue worktree 생성 전 기준 브랜치(`main`)로 전환하고 최신 원격 변경을 `git pull`로 반영한 뒤 worktree를 생성한다. 이 절차는 `scripts/start-issue-worktree.sh`가 수행한다.
- 브랜치명은 `issue/{이슈번호}-{slug}` 형식을 사용한다. `{slug}`는 이슈 제목을 요약한 짧은 kebab-case다.
- issue worktree 안에서 작업을 시작할 때만 `git branch --show-current`와 `git status`로 현재 브랜치와 변경사항을 확인한다.
- worktree 사용 시 plan의 `worktree` 경로와 현재 작업 디렉토리가 일치해야 한다.
- 현재 브랜치가 plan의 `branch`와 다르면 구현을 중단한다.
- 작업 시작 전과 커밋 전 `/Users/thlee/Documents/personal/stock-market/scripts/check-plan-conflicts.sh {이슈번호}`를 실행한다.
- 충돌 검사 실패 시 병렬 진행을 중단하고, 충돌 issue 완료 후 순차 처리하거나 plan의 `allowed_paths`를 좁힌 뒤 재승인받는다.
- Implementation/Review 작업으로 새 파일을 만들면 완료 전 `git add -N {new-file}`을 실행해 `git diff`에서 신규 파일 내용이 보이도록 한다.
- `git add -N`은 intent-to-add 용도이며 실제 내용을 stage하지 않는다. 실제 `git add`는 커밋 단계 또는 태형님이 명시적으로 요청한 경우에만 실행한다.
- 기존 tracked 파일 수정은 `git add -N` 대상이 아니며 `git diff`로 확인한다.
- 빌드 산출물(`build/`, `bin/`), 비밀값 파일(`.env*`), 태형님이 제외 요청한 파일은 stage 대상에서 제외한다.
- 커밋 메시지에는 AI/도구 작성자 정보를 포함하지 않는다. 금지 예: `Co-Authored-By`, `Generated by`, `Built with`, `Assisted by`.
- 태형님이 명시적으로 커밋 또는 push를 하지 말라고 지시한 경우에는 완료 의사 기반 커밋/push를 수행하지 않는다.

## Pull Request Harness

- issue 기반 Implementation 작업에서 완료 의사를 보이면 commit/push 이후 `gh pr create`로 PR을 생성한다.
- 같은 브랜치의 열린 PR이 이미 있으면 새 PR을 만들지 않고 기존 PR URL을 사용한다.
- PR 제목은 `#{이슈번호} {작업 요약}` 형식을 기본으로 한다.
- PR 본문은 `작업 요약`, `주요 변경사항`, `검증` 중심으로 작성하고 `Closes #{이슈번호}`를 포함한다.
- PR 본문에는 plan 문서, brainstorm 문서, 분석 문서 같은 내부 작업용 md 파일 경로를 포함하지 않는다.
- PR 본문에는 `docs/plans/**`, `docs/brainstorms/**`, `.claude/designs/**`, `.claude/analyzes/**` 경로를 쓰지 않는다.
- PR 설명에는 AI/도구 작성자 정보를 포함하지 않는다.
- PR 생성 또는 기존 PR 확인에 실패하면 Implementation PR Gate 실패로 보고하고 최종 완료 응답을 하지 않는다.
- 태형님이 명시적으로 PR 생성을 금지한 경우에만 PR 생성을 생략한다.
- PR 이후 자동 리뷰 게이트는 없다. 완료 판정 근거는 review 단계의 `/ce:review` 결과와 태형님이 선택한 검증 결과다.

## Implementation PR Gate

issue 기반 Implementation 작업에서 완료 의사를 보이면 최종 응답 전에 아래 순서대로 처리한다. 이 Gate는 stage `pr` 단계에 해당한다.

1. 가능한 검증을 실행한다.
2. plan 체크리스트를 실제 작업 상태와 일치시킨다. 이 단계에서는 plan `status`를 `done`으로 전환하지 않는다.
3. 커밋 전 `/Users/thlee/Documents/personal/stock-market/scripts/check-plan-conflicts.sh {이슈번호}`를 실행한다.
4. 작업 범위 변경만 stage하고 커밋한다.
5. 현재 작업 브랜치를 원격에 push한다.
6. `gh pr create`로 PR을 생성하거나 같은 브랜치의 기존 열린 PR URL을 확인한다.
7. stage 마커를 `merge`로 갱신하고 태형님에게 PR URL과 함께 병합 여부를 확인한다.

완료 의사란 에이전트가 최종 응답에서 구현/수정/검증 완료를 보고하려는 경우, PR 생성을 포함한 구현 단계 마무리를 보고하려는 경우, 또는 태형님이 "완료해", "마무리해", "끝내줘", "정리해줘"처럼 완료 처리를 지시한 경우다.

아래 조건에서는 Implementation PR Gate를 수행하지 않는다.

- 이슈 번호가 `TBD`인 작업
- 현재 작업이 issue 기반이 아닌 작업
- 태형님이 명시적으로 커밋 또는 push를 하지 말라고 지시한 작업

태형님이 명시적으로 PR 생성을 금지한 경우에는 PR 생성 단계만 생략하고 최종 응답에 이유를 명시한다.

## Merge Gate

PR 생성 후 아래 순서대로 처리한다. 이 Gate는 stage `merge` 단계에 해당한다.

1. 태형님 병합 승인을 확인한다. 승인 없이 `gh pr merge`를 실행하지 않는다.
2. 구현 이해 확인 Gate 이후 코드 변경이 있었는지 확인하고, 있으면 [notion-guide.md](../notion-guide.md)에 따라 Implementation 페이지를 갱신한다.
3. plan 체크리스트를 최종 상태와 일치시키고 plan `status`를 `done`으로 전환한다.
4. `gh pr merge`로 병합한다. 병합 방식(merge/squash/rebase)은 병합 시점에 태형님 선택을 따르고, 지정이 없으면 squash를 기본으로 한다.
5. 병합으로 이슈가 자동 close됐는지 확인한다(`Closes #{이슈번호}` 기준).
6. Final Cleanup Gate를 수행한다.

병합 전 태형님이 추가 수정을 요청하면 같은 브랜치에서 수정, 검증, 추가 commit/push로 기존 PR을 업데이트한다. 수정이 plan 범위를 벗어나면 즉시 중단하고 plan 업데이트와 재승인을 요청한다.

## Final Cleanup Gate

병합까지 성공하면 마지막 단계로 issue worktree를 정리하고 메인 저장소 로컬 `main`을 최신화한다.

Final Cleanup Gate는 issue worktree 기반 작업에만 적용한다. worktree가 아닌 작업, 이슈 번호가 `TBD`인 작업, 태형님이 명시적으로 worktree 정리를 금지한 작업에는 적용하지 않는다.

정리 전 아래를 확인한다.

1. 정리 대상 worktree가 plan의 `worktree`와 일치한다.
2. 정리 대상 worktree가 main/master worktree가 아니다.
3. `git status --short` 기준 uncommitted 변경과 untracked 파일이 없다.
4. 로컬 브랜치의 commit이 원격에 모두 push되어 있다.
5. 현재 작업 브랜치의 PR 병합과 이슈 close가 모두 끝났다.

정리 순서는 아래를 따른다.

1. 메인 저장소에서 `git worktree list`로 issue worktree 경로를 확인한다.
2. `git worktree remove {plan.worktree}`로 issue worktree를 제거한다.
3. 메인 저장소에서 `git checkout main`을 수행한다.
4. 메인 저장소의 로컬 `main`에서 `git pull`을 수행해 최신 원격 변경을 반영한다.
5. 병합된 로컬 브랜치가 남아 있으면 `git branch -d issue/{이슈번호}-{slug}`로 제거한다.

정리 중 하나라도 실패하면 전체 완료로 보고하지 않고 실패 원인과 남은 정리 작업을 보고한다. dirty 상태, untracked 파일, 미push commit이 있으면 worktree를 제거하지 않는다.
