## What We're Building

"연도별 추세" 화면 하단의 **전체 재무제표 세부 계정** 표를, 지금의 "평면 한 줄씩 나열"에서
DART 실제 보고서처럼 **2단계 계층 트리**로 바꾼다.

- 예: `유동자산` 아래에 `현금및현금성자산 / 매출채권 / 재고자산 …` 하위 항목을 접이식으로 묶는다.
- 각 항목: 연도별 값(기존) + **전년 대비 증감(▲빨강 / ▼파랑, %)** 표시 → "카테고리 안에서 뭐가 늘고 줄었는지" 한눈에.
- 대상: 재무제표 종류별(BS/IS/CIS/CF/SCE) 섹션 각각. BS(재무상태표)에서 효과 최대, IS/CF는 계층이 얕아 덜 극적이지만 동일 로직 적용.

### 현재 상태 (문제)

- 백엔드 `FinancialTimelineAssembler.toDetailGroups()`가 `statementDiv`(BS/IS/…)별로만 그룹핑하고, 그 안은 `mergeRows()`로 **평면 `List<TimelineRow>`**를 만든다.
- 프론트 `getTimelineDetailGroups()` → `portfolio-deposit-financial.html`의 접이식 섹션이 그 평면 행을 그대로 `<tr>` 반복 렌더한다.
- 즉 한 재무제표 종류(예: BS) 안의 수십 개 계정이 계층 없이 한 줄씩 다 나온다.

### 핵심 기술 사실 (DART `fnlttSinglAcntAll` 실호출로 확인됨)

- 응답에 **명시적 계층 필드 없음**: `account_detail`은 "-", `ord`는 평면 순번(깊이 정보 아님).
- 계층은 `account_id`(IFRS 표준코드)에 **암묵적**으로만 존재. 응답 순서는 `[총계 → 카테고리 → 하위항목 → 다음 카테고리 …]`.
- 순서 특성상 **총계(자산총계)가 하위 항목보다 먼저** 나온다 → 렌더 순서 보정 필요.
- `account_id`가 `-표준계정코드 미사용-` 또는 `dart_*` 커스텀이라 표준 분류 불가한 항목 존재.

### 코드 확인 결과 (구현 관점 사실)

- `DartFinancialAdapter.getFullFinancialStatements()` → `.stream().map(...).toList()`로 **DART 응답 순서를 그대로 보존**한다.
- `FinancialTimelineAssembler.mergeRows()`는 `newestFirst`(최신 연도 우선) + `LinkedHashMap`으로 병합 → **결과 행 순서 = 최신 연도 응답의 DART 원본 순서**. 즉 병합 후에도 `[총계 → 카테고리 → 하위 → …]` 순서가 유지된다. **순서 기반 그룹핑의 전제가 성립함.**
- `FullFinancialStatement`(domain record)는 `accountId`를 이미 보유(현재 병합 키로 사용 중). `ord`는 domain에 매핑돼 있지 않으나, 위처럼 리스트 순서로 대체 가능하므로 추가 매핑 불필요.
- `TimelineDetailGroup { statementDiv, statementName, List<TimelineRow> accounts }`, `TimelineRow { id, name, Map<year,value> values }` 구조.

## Why This Approach

- **DART가 계층을 안 주므로 우리가 복원한다**: 명시적 depth가 없고 `account_id`에만 암묵적으로 존재 → IFRS 앵커 상수 + 순서 기반 그룹핑으로 2단계 트리를 재구성한다.
- **순서 기반이 이름/코드 매칭보다 견고**: 하위 항목의 `account_id`는 커스텀(`dart_*`)이 잦지만, "카테고리 앵커 다음부터 다음 앵커 전까지"라는 **위치 규칙**은 커스텀 코드에도 동작한다. 하위 항목 자체의 코드 표준성에 의존하지 않는다.
- **단일 회사 전용이라 안정적**: 이 화면은 이미 "단일 회사 딥 시계열"(비교용 아님)이 전제. 연도 간 계정 구성이 안정적이고 `account_id`로 매칭되므로 트리 구조도 안정적으로 재현된다.
- **기존 병합 파이프라인 재활용**: 순서가 이미 보존되므로, 병합된 평면 행 위에 "앵커 감지 → 구간 분할"만 얹으면 된다. 데이터 수집/호출 로직은 손대지 않는다.

## 핵심 설계: 계층 복원 알고리즘

### 앵커 레지스트리 (statementDiv별 IFRS 카테고리 id 상수)

재무제표 종류별로 "카테고리 헤더로 인정할 `account_id` 집합"을 상수로 유지한다(확장 가능).

**BS(재무상태표) — 8개 앵커, 2가지 역할로 구분:**

- **총계(GRAND_TOTAL)** — 섹션 합계, 접이식 아님. depth 0의 강조 행:
  - `ifrs-full_Assets` (자산총계)
  - `ifrs-full_Liabilities` (부채총계)
  - `ifrs-full_Equity` (자본총계)
  - `ifrs-full_EquityAndLiabilities` (자본과부채총계)
- **카테고리(CATEGORY)** — 접이식 부모(children을 가짐):
  - `ifrs-full_CurrentAssets` (유동자산)
  - `ifrs-full_NoncurrentAssets` (비유동자산)
  - `ifrs-full_CurrentLiabilities` (유동부채)
  - `ifrs-full_NoncurrentLiabilities` (비유동부채)

**IS / CIS / SCE:** 초기 앵커 없음(계층이 얕거나 순차 소계 구조라 컨테이너 의미가 약함) → 폴백(아래) 규칙에 따라 **평면 렌더 유지**.

**CF(현금흐름표):** 선택적으로 3개 활동 앵커를 CATEGORY로 추가 검토(플랜에서 결정):
`ifrs-full_CashFlowsFromUsedInOperatingActivities`(영업), `...InvestingActivities`(투자), `...FinancingActivities`(재무).
※ CF 하위는 표준코드 미사용이 잦아 순서 기반 그룹핑이 특히 유효.

### 그룹핑 규칙 (순서 기반, 최신 연도 순서 기준으로 이미 정렬된 행 위에서)

한 statement 그룹의 병합 행 리스트를 위→아래로 훑으며:

1. `account_id`가 **GRAND_TOTAL 앵커** → depth 0 총계 행(자식 없음, 토글 없음).
2. `account_id`가 **CATEGORY 앵커** → 새 카테고리 부모 시작(접이식). 이후 항목들을 이 부모의 자식으로.
3. 그 외 항목 → **직전 CATEGORY 부모의 자식**. 직전 카테고리가 아직 없으면(=선두 orphan) → `기타(미분류)` 폴백 그룹으로.
4. 어떤 카테고리 앵커도 감지되지 않은 statement(IS 등) → 그룹 전체를 **평면 렌더**(현행과 동일, "기타(미분류)" 래퍼로 감싸지 않음).

### "기타(미분류)" 폴백 — 확정 결정 반영

- **항목 이름은 DART 원본 그대로 유지**한다. 이름을 "기타"로 바꾸는 게 아니라 **위치만** 미분류 그룹으로 모은다.
- 폴백에 들어가는 경우: (a) 첫 카테고리 앵커보다 앞에 나온 orphan 항목, (b) 카테고리 구조 자체가 없는 statement는 §4에 따라 평면 렌더(폴백 그룹 미사용).
- 하위 항목의 `account_id`가 커스텀/미사용이어도, **순서상 카테고리 밑에 있으면 그 카테고리 자식**이다(폴백 아님). 폴백은 "붙일 부모가 없을 때"만.

### 총계 순서 보정

DART 순서가 `자산총계 → 유동자산 → …`라 총계가 카테고리보다 먼저 온다. 렌더 시:
- GRAND_TOTAL 행은 감지 위치 그대로 depth 0에 두되, 시각적으로 **섹션 헤더(강조/굵게)**로 표시.
- 결과 트리(BS 예):
  ```
  자산총계                      (총계, 강조)
  ▸ 유동자산                    (카테고리, 접이식)
      현금및현금성자산 / 매출채권 / 재고자산 …   (자식)
  ▸ 비유동자산
      유형자산 / 무형자산 …
  부채총계                      (총계, 강조)
  ▸ 유동부채 → …
  ▸ 비유동부채 → …
  자본총계                      (총계, 강조)
  ▸ 자본 카테고리 → …
  ```

### 전년 대비 증감(YoY) 표시

- 각 셀(연도 값) 옆/아래에 직전 연도 대비 증감률을 `▲12.3%`(빨강)/`▼8.1%`(파랑)로 병기.
- 계산: `(당해 - 직전) / |직전| × 100`. 직전 연도 값이 없거나 0이면 표기 생략("-").
- **진행중(partial) 연도**는 누적(YTD) 기준이라 직전 연간과 직접 비교 시 착시 → 증감 표기 생략(값만 표시). (요약 표/지수 표의 partial 처리와 일관.)
- 기존 `getFinancialSummaryCards`에 이미 유사 changeRate 계산 로직이 있어 헬퍼 재사용/참고 가능.

## Key Decisions

### 지난 논의에서 확정된 사항 (재확인)

| 결정 | 내용 |
|------|------|
| 트리 깊이 | 2단계: 카테고리(부모) → 하위 항목(자식) |
| 각 항목 표기 | 연도별 값 + 전년比 증감(▲빨강/▼파랑, %) |
| 미분류 항목 이름 | **DART 원본 이름 유지**, 위치만 "기타(미분류)" 그룹으로 |
| 대상 재무제표 | BS 효과 최대, IS/CF는 얕지만 동일 로직 적용 |
| 앵커 목록 | 코드 상수(BS 8개 기준, 확장 가능) |
| 범위 | "연도별 추세"의 세부 계정 표만. 요약 표/차트는 그대로 |

### 이번 브레인스톰에서 새로 제안하는 사항 (확인 필요)

| 항목 | 제안 | 이유 |
|------|------|------|
| 앵커 역할 2분류 | 총계(GRAND_TOTAL, 비접이식 강조행) vs 카테고리(CATEGORY, 접이식 부모)로 구분 | BS 8앵커에 자산총계 같은 "총계"와 유동자산 같은 "카테고리"가 섞임. 총계를 접이식 부모로 만들면 자식 없는 빈 토글이 생김 → 총계는 강조 행으로 |
| 앵커 없는 statement | IS/CIS/SCE는 **평면 렌더 유지**(미분류 래퍼로 감싸지 않음) | 앵커가 하나도 없으면 전 항목이 "기타(미분류)"에 들어가 오히려 현행보다 나쁨. 계층이 의미 있을 때만 트리화 |
| CF 앵커 | 영업/투자/재무 3개 활동 앵커 추가 검토 | CF에 2단계 트리 의미 부여. 단 하위 표준코드 미사용 잦음 → 순서 기반이 특히 유효. 플랜에서 확정 |
| 기본 펼침 상태 | 카테고리는 기본 **접힘**, statement 섹션은 기존대로(예: IS만 펼침) | 카테고리까지 다 펼치면 화면이 다시 길어짐 |

### 계층 생성 위치: 백엔드 vs 프론트 (플랜에서 최종 결정)

| 방식 | 장점 | 단점 |
|------|------|------|
| **백엔드** (응답 DTO에 계층 반영: `TimelineDetailGroup`에 카테고리 노드 중첩 또는 `TimelineRow`에 `depth`/`parentId`/`role` 추가) | IFRS 앵커 상수·순서 규칙을 Java 한 곳에 집중, 테스트 가능(순수 함수), 프론트는 렌더만. 아키텍처상 "재무 도메인 규칙"에 부합 | 응답 DTO 스키마 변경(Approval Gate: public API 응답 형태 변경). 기존 프론트 렌더 로직 수정 동반 |
| **프론트** (평면 응답 그대로 두고 JS에서 `account_id` 앵커로 그룹핑) | 백엔드/DTO 무변경, 서버 리스크 0 | 앵커 상수·규칙이 JS에 상주(테스트 약함), `account_id`가 응답에 필요한데 현재 `TimelineRow.id`가 account_id를 담는지 확인 필요, 로직이 표현층에 섞임 |

- **성향(권장)**: **백엔드**. 앵커 레지스트리·순서 규칙·총계/카테고리 분류는 재무 표현이 아니라 **데이터 구조 해석 로직**이라 application 계층 + 단위테스트가 자연스럽다. 다만 응답 DTO 형태 변경은 **Approval Gate**에 해당하므로 플랜에서 스키마안을 확정하고 사용자 승인 후 진행.
- 참고: `TimelineRow.id`는 현재 `detailRowKey`(account_id 우선, 미사용이면 계정명) 값을 담는다. 프론트 방식을 택할 경우 앵커 매칭에 이 `id`(=account_id)를 그대로 쓸 수 있으나, "미사용" 계정은 계정명이 들어가 있어 앵커 매칭에는 문제없음(앵커는 표준 id만 매칭).

## Edge Cases

- **총계만 있고 카테고리 없음**: 아주 단순한 재무제표. GRAND_TOTAL만 감지 → 총계 행 + 나머지 평면. 트리 효과 없지만 깨지지 않음.
- **카테고리 앵커가 특정 연도에만 존재**: 병합 행 순서는 최신 연도 기준. 과거에만 있던 항목은 뒤에 붙음 → 그 항목이 어느 카테고리에 속하는지 애매할 수 있음. 최신 연도 구조를 정본으로 삼고, 최신에 없던 orphan은 "기타(미분류)".
- **하위 항목이 커스텀 account_id**: 순서상 카테고리 밑이면 그 자식으로(정상). 폴백 아님.
- **선두 orphan**: 첫 카테고리 앵커 전에 나온 비(非)총계 항목 → "기타(미분류)".
- **진행중(partial) 연도 YoY**: 누적 기준 → 증감 표기 생략(값만).
- **직전 연도 값 0 또는 없음**: 증감 분모 불가 → "-".
- **개별/연결(fsDiv) 전환**: 트리 구조는 fsDiv와 무관하게 동일 로직. 데이터만 달라짐.
- **동일 account_id 중복 등장**: 이론상 카테고리 앵커가 두 번 나오면 두 번째부터 새 부모로 시작(순서 규칙 그대로). 실호출상 드묾 — 방어적으로 허용.
- **행 수 많은 statement 접힘 성능**: 기존과 동일(섹션 접기). 카테고리 접힘으로 오히려 초기 렌더 부담 감소.

## 범위 밖 (하지 않음)

- 요약 표/차트, 재무지표 4분류 표, 공시 탭 — 그대로.
- 3단계 이상 트리(총계>카테고리>중분류>항목) — 이번엔 2단계까지.
- DART 원문 XBRL 파싱으로 진짜 계층 트리 복원 — 하지 않음(앵커+순서 휴리스틱으로 충분).
- 다른 회사와의 비교 — 이 화면은 단일 회사 전용 전제 유지.
- 데이터 수집/호출 로직 변경 — 병합 후단만 손댐.
