## 요청 이해
자동납입(월 납입액·납입일)을 설정한 적금에 "납입 처리 방식" 선택값을 둔다.
- 알림 확인: 지금처럼 납입일에 알림이 뜨고, 사용자가 눌러서 납입을 기록한다.
- 자동 반영: 납입일이 되면 시스템이 월 납입액을 납입 이력에 기록하고 원금(투자 금액)을 늘린다.

## 문제 정의
- 자동납입 설정은 납입 예정 정보일 뿐이다. 실제 기록은 언제나 사람이 해야 한다.
- 은행 자동이체로 빠져나가는 적금도 매달 앱에서 직접 납입해야 원금이 맞는다.
- 2026-04-10 추가 납입 설계는 "실제 납입 여부를 확인할 수 없다"는 이유로 자동 스케줄 방식을 뺐다. #99도 "완전 자동 기록 대신 알림 + 사용자 확인"을 전제로 한다. 이번 요청은 이 결정을 항목별 선택으로 바꾼다.

## 목표
- 자동납입을 설정할 때 처리 방식(알림 확인 / 자동 반영)을 고를 수 있다.
- 자동 반영 항목은 납입일에 사람 손 없이 납입 이력과 원금이 갱신된다.
- 알림 확인 항목과 기존 데이터는 지금과 똑같이 동작한다.

## 범위
권장안 기준이며 확인 후 확정한다.
- 백엔드: 현금성 자산 상세에 처리 방식 저장(컬럼 1개), 등록·수정 요청과 응답에 필드 추가, 처리 방식 검증, 납입일 자동 기록 일배치(스케줄러 + 배치 서비스)
- 프론트: 등록·수정 모달의 자동납입 설정에 처리 방식 선택, 보유 자산 설명 줄에 자동 납입 표시

## 제외 범위
- 메일 알림, 알림 on/off 설정(#99 요구 1·3)
- 은행 계좌·자동이체 연동(실제 출금 여부 확인)
- 납입 이력(`deposit_history`) 구조 변경
- 기존 미납·당일 판정 규칙 변경(확인 6에서 포함 여부를 정한다)

## 현재 코드 확인 결과
- **자동납입 설정:** `CashDetail`에 월 납입액·납입일이 있다(`CashDetail.java:17-18`). 테이블은 `cash_detail.monthly_deposit_amount`·`deposit_day`다(`CashItemEntity.java:32-36`). 펀드·연금 상세도 같은 두 칸이 있다. 처리 방식을 담는 값은 없다.
- **입력 화면:** 현금성 자산 폼의 "자동납입 설정"(월 납입액·납입일)은 예금·적금·CMA 구분 없이 보인다(`portfolio-add.html:314-328`, `portfolio-edit.html:253-267`).
- **납입 기록:** `addDeposit`이 `DepositHistory`를 저장하고 `restoreAmount`로 원금을 늘린다(`PortfolioService.java:1110-1124`). 대상은 현금성·펀드·연금이다(`:1262`).
- **알림(리마인더):** 로그인 때 `checkDepositReminder()`가 항목의 `depositDueToday`·`depositOverdue`로 팝업을 띄운다(`portfolio.js:2247-2260`, `app.js:193`). [납입]을 누르면 금액이 빈 납입 창이 열린다(`portfolio.js:2204-2211, 2273-2279`).
- **판정 규칙:** 납입일은 말일 보정(`min(납입일, 그달 일수)`)하고, 이번 달 1일~오늘 기록이 있는지 본다(`PortfolioService.java:1204-1260`). 판정 대상은 현금성·펀드뿐이고 연금은 빠져 있다(`:382`).
- **기간:** 판정은 시작일·만기일을 보지 않는다. 만기가 지난 적금도 납입일 설정이 남아 있으면 매달 알림 대상이 된다.
- **스케줄러 관례:** `@Scheduled(cron = "${...}", zone = "Asia/Seoul")`와 `LoggingContext.forScheduler`를 쓴다(`PortfolioSnapshotScheduler.java:21-23`). 배치 서비스는 트랜잭션 없이 대상별로 실패를 격리한다(`PortfolioSnapshotBatchService.java:22-23, 83-88`). 스케줄러 풀은 10이다(`application.yml:40-45`).
- **날짜 기준:** 컨테이너에 TZ 설정이 없다(`Dockerfile`, `docker-compose.yml`). JVM 기본 시간대가 UTC면 `LocalDate.now()`가 한국 0~9시에 전날을 돌려준다. #113은 `Clock.system(Asia/Seoul)`을 주입해 KST로 계산한다(`PortfolioIncomeService.java:53, 67`).
- **화면 날짜 기본값:** 납입 창의 기본 납입일은 `toISOString()`(UTC)이라 한국 오전 9시 전에는 전날로 채워진다(`portfolio.js:2206`). 리마인더는 이미 현지 날짜를 쓴다(`:2233-2237`).
- **DB:** `ddl-auto: update`라 nullable 컬럼 추가는 자동 반영된다. 스키마 변경은 `db/migration`에 SQL로 남긴다(`portfolio_item_institution_2026_10_03.sql`).

## 후보 접근

### 자동 반영 방식
- **A. 납입일 일배치**
  - 매일 00:10(KST) 스케줄러가 "자동 반영 + 오늘이 납입일 + 이번 달 기록 없음 + 기간 안" 항목에 납입 이력을 만든다. 처리는 기존 납입 추가와 같다(이력 저장 + 원금 증가).
  - 장점: 기존 스케줄러·배치 관례 그대로다. 조회 경로에 쓰기가 섞이지 않는다. 놓친 날은 기존 미납 알림으로 넘어간다.
  - 단점: 서버가 그 시각에 꺼져 있으면 그달 자동 기록이 빠진다(미납 알림으로 대신 알린다).
- **B. 조회 때 따라잡기**
  - 로그인·목록 조회 때 지난 납입일을 계산해 기록한다.
  - 장점: 스케줄러가 필요 없고 서버 중단과 무관하다.
  - 단점: 읽기 API가 쓰기를 한다(트랜잭션 경계, 동시 조회 중복). 접속하지 않으면 원금 추이·스냅샷 반영이 늦다.
- **C. 일배치 + 이번 달 누락분 소급**
  - A에 더해, 납입일이 지났는데 기록이 없으면 납입일 날짜로 소급 기록한다.
  - 장점: 서버 중단에 강하다.
  - 단점: 이번 달 납입분을 원금에 넣은 채 월 중간에 등록하거나 자동 반영으로 바꾸면 이중 계상된다. 실제로 빠진 달과 구분할 수 없다.

### 처리 방식 저장
- **가. `cash_detail`에 처리 방식 컬럼 1개**
  - 값은 알림 확인/자동 반영 두 가지, nullable이다. null은 알림 확인으로 읽어 기존 데이터를 바꾸지 않는다.
- **나. 불리언 컬럼(자동 반영 여부)**
  - 단순하지만 화면의 "처리 방식" 선택과 이름이 어긋나고, 방식이 늘면 컬럼을 다시 바꿔야 한다.
- **다. `portfolio_item` 공통 컬럼**
  - 펀드·연금까지 한 번에 쓸 수 있지만, 자동납입이 없는 자산군에도 칸이 생긴다.

## 권장 접근
- **대상:** 현금성 자산(예금·적금·CMA). 같은 상세·같은 입력 폼을 쓰므로 적금만 따로 가르지 않는다.
- **저장:** 가. `cash_detail`에 처리 방식 컬럼(가칭 `deposit_mode VARCHAR(20) NULL`)과 도메인 enum(가칭 `DepositMode`: 알림 확인/자동 반영)을 둔다.
  - 자동 반영이면 월 납입액(0 초과)과 납입일이 꼭 있어야 한다. 없으면 저장을 거부한다.
- **자동 반영:** A. 매일 00:10(KST) 일배치로 아래 조건을 모두 만족하는 항목을 기록한다.
  1. 처리 방식이 자동 반영이고 월 납입액·납입일이 있다.
  2. 오늘(KST)이 이번 달 납입일이다. 말일 보정은 기존 규칙과 같다.
  3. 이번 달 1일~오늘 납입 기록이 없다. 직접 기록했으면 건너뛴다.
  4. 시작일 이후이고 만기일 전이다. 비어 있는 날짜는 조건에서 뺀다.
  - 기록 내용: 납입일 = 오늘, 금액 = 월 납입액, 메모 "자동 납입". 원금 증가는 기존 납입 추가와 같다.
  - 항목별 트랜잭션으로 실패를 격리하고, 트랜잭션 안에서 조건 3을 다시 확인해 중복을 막는다.
  - 날짜는 KST `Clock`을 주입해 계산한다.
- **알림 확인:** 지금 동작을 유지한다(확인 4 결과 반영).
- **화면:** 자동납입 설정 아래에 "납입 처리" 선택(알림 받고 직접 납입 / 납입일에 자동 납입)을 둔다. 보유 자산 설명 줄에 "자동 납입"을 표시한다.
- **리마인더:** 바꾸지 않는다. 자동 기록이 되면 이번 달 기록이 생겨 알림 대상에서 빠진다. 배치가 실패하면 기존처럼 당일·미납 알림이 떠서 안전망이 된다.

## 결정 사항 (요청에서 확정)
- 자동납입 설정 항목에 처리 방식 선택값을 둔다: 알림 받고 클릭(현행) / 납입일 자동 입금.
- 자동 입금은 납입일 당일에 반영한다.

## 태형님 확인 필요
1. **대상 자산**
   - 권장: 현금성 자산(예금·적금·CMA) 전체. 같은 입력 폼·같은 상세라 적금만 가르면 예외가 생긴다.
   - 대안 1: 적금만(예금·CMA에는 선택칸을 숨긴다).
   - 대안 2: 펀드·연금까지. 펀드는 좌수 없이 금액만 기록되고, 연금은 지금 알림 대상이 아니다.
2. **자동 반영 시점과 놓친 날**
   - 권장: 납입일 00:10(KST)에 하루 한 번. 서버가 그 시각에 꺼져 있었으면 소급하지 않고 기존 당일·미납 알림으로 넘긴다.
   - 대안 1: 납입일 동안 매시 재시도. 자동 기록을 지우면 같은 날 다시 생기므로 "처리함" 표시 컬럼이 더 필요하다.
   - 대안 2: 이번 달 누락분 소급(C). 월 중간 등록·전환 때 이중 계상 위험이 있다.
3. **기간과 기본값**
   - 권장: 시작일 전과 만기일 당일 이후에는 자동 기록하지 않는다. 기존 항목과 새 항목의 기본값은 알림 확인이다.
4. **알림 확인 방식의 [납입] 동작**
   - 권장: 지금처럼 납입 창을 열되 금액(월 납입액)과 날짜(오늘, 현지 날짜)를 미리 채워 "납입 추가"만 누르면 되게 한다.
   - 대안: 지금 그대로 둔다(금액 직접 입력).
5. **자동 기록 안내**
   - 권장: 별도 알림 없이 납입 이력 메모 "자동 납입"으로 구분하고, 보유 자산 설명 줄에 "자동 납입"을 표시한다.
   - 대안: 로그인 팝업에 "오늘 자동 납입된 항목" 안내를 더한다.
6. **만기 지난 항목 알림** (현재 코드에서 발견한 기존 동작)
   - 현황: 미납·당일 판정이 만기일을 보지 않는다. 만기 뒤에도 납입일 설정이 남아 있으면 매달 알림이 뜬다.
   - 권장: 이번 범위에서 뺀다(기존 판정 규칙 불변). 필요하면 후속 이슈로 둔다.
   - 대안: 이번에 같이 고친다(판정 규칙 변경).
7. **이슈와 진행 방식**
   - 권장: 새 이슈로 등록한다. #99는 메일·알림 설정 범위로 두고, 새 이슈 본문에 "자동 기록 대신 사용자 확인" 전제를 항목별 선택으로 바꾼다고 적는다.
   - 세션 브랜치와 하네스 절차를 따른다. DB는 nullable 컬럼 추가로 하고 plan의 DB 스키마 리뷰에서 확정한다.
   - 단위 테스트는 처리 방식 검증, 자동 기록 판정(납입일·말일 보정·기간·중복), 배치 실패 격리를 상태 기반으로 작성한다. 시나리오는 plan 단계에서 따로 승인받는다.
   - 대안: #99에 합쳐 함께 진행한다.
