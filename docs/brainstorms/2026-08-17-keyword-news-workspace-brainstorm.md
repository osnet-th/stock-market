## 문제 정의

태형님이 제시한 목업(`~/Downloads/키워드 뉴스 워크스페이스 (단일파일).html`)대로
**키워드 페이지와 뉴스 검색 페이지를 하나의 화면으로 통합**한다.

현재는 좌측 메뉴가 두 개로 갈라져 있다.

- `키워드`(`partials/keywords.html`, 206줄) — 키워드 CRUD + 카드 클릭 시 아코디언으로 해당 키워드 뉴스 펼침
- `뉴스 검색`(`partials/news-search.html`, 99줄) — ES 전문 검색, 검색어 없이는 아무것도 못 봄

두 화면이 같은 데이터(수집된 뉴스)를 다루는데 진입점이 나뉘어 있어,
"내 키워드 중 이 두 개 안에서만 검색" 같은 자연스러운 동작이 불가능하다.

### 핵심 상호작용

- **키워드 = 필터**: 좌측 레일에서 키워드를 클릭하면 선택(다중)되고, 우측 뉴스 스트림이 그 키워드들로 좁혀진다. 선택 시 상단 검색 placeholder가 `선택한 키워드 N개 안에서 검색`으로 바뀐다.
- **검색창은 항상 노출**: 검색어가 없으면 "저장된 전체 뉴스", 있으면 "'X' 검색 결과". 즉 **검색어 없이도 뉴스 열람이 가능**하다.
- **날짜별 그룹**: 뉴스 스트림이 `오늘 · 2026.08.17 (월) 4건` 헤더로 일자 구분된다.
- 키워드 카드에 **7일 스파크라인 + 총 건수 + 오늘 증가분 + 마지막 성공 시각**이 붙는다.
- 상단에 **수집 스케줄 상태**(마지막/다음 실행)와 **연속 실패 키워드** 뱃지가 있다.

디자인 토큰(`#eef0f3` 배경 / `#1f4f9e` blue / `#c02a22` red / IBM Plex)은 #114에서
`css/custom.css`의 `--dc-*`로 이미 도입돼 있어 추가 도입이 필요 없다.

### 제약 1 — 검색어 없는 열람이 현재 불가

목업의 기본 상태가 "저장된 전체 뉴스"다. 지금 `GET /api/news/search`는 `query` 가 `@NotBlank` 라
빈 검색어를 400으로 막는다. 통합 화면의 **기본 화면이 곧 이 상태**라 반드시 풀어야 한다.

### 제약 2 — 키워드 통계는 N+1 유발

키워드 14개 화면에 건수·오늘·마지막성공·7일 스파크라인을 그리려면 키워드마다 4종 집계가 필요하다.
`GROUP BY keyword_id` 한 방 + 7일 `GROUP BY keyword_id, DATE(created_at)` 한 방으로 묶어
**단일 통계 엔드포인트**로 내려야 한다.

### 제약 3 — 목업의 일부는 백엔드 신규 도메인을 요구한다

- **연속 실패**: 수집 시도 이력(성공/실패/연속실패일수)을 남기는 테이블이 없다. 새 Entity가 필요하다.
- **읽음/저장**: 사용자×뉴스 상태 테이블이 필요하다. 또는 localStorage로 기기 한정 처리.
- **유사 기사**: 제목 유사도 클러스터링. 서버 배치 or 조회 시점 계산 모두 비용이 있다.
- **언론사**: 수집 어댑터가 언론사를 저장하지 않는다. `originalUrl` 도메인 매핑으로 근사 가능하나 정확하지 않다.

이 4개는 **디자인 픽셀은 그대로 두면서도, 데이터가 없으면 못 그리는** 항목이다.

### 충돌 1 — `이름 · 수집 범위 수정`: Keyword 는 공유 리소스다

`Keyword` 클래스 주석이 명시한다 — `키워드 도메인 모델 (공유 리소스)`.
`KeywordServiceImpl.registerKeyword()` 가 `findByKeywordAndRegion(...).orElseGet(create)` 로
**같은 (이름, 지역) 을 여러 사용자가 공유**하고, 사용자별 상태는 `UserKeyword.active` 에만 있다.
`Keyword` 에는 **이름·지역을 바꾸는 메서드가 아예 없다**(불변).

그래서 rename 을 단순 UPDATE 로 구현하면:
- 같은 키워드를 구독한 **다른 사용자의 키워드까지 바뀐다**
- `region` 은 자연키(`findByKeywordAndRegion`)의 일부라 변경 시 **기존 행과 충돌**할 수 있다
- `news.keyword_id` 로 묶인 기존 기사는 새 이름과 무관해진다

또한 목업 문구는 "이미 수집된 기사 N건은 이름을 바꿔도 **그대로 유지**"를 약속하는데,
`unsubscribeKeyword()` 는 마지막 구독자가 떠나면 `news` 를 **삭제**한다.

선택지:
- **(A) 재구독 방식** — 수정 = 새 `(이름, 지역)` 구독 + 기존 구독 해제. 다른 사용자 영향 0.
  단독 구독자면 `news.keyword_id` 를 새 키워드로 **이관**해 목업 약속을 지킨다.
  다중 구독자면 기존 기사가 옛 키워드에 남으므로 문구 조정 필요.
- (B) Keyword 를 사용자 소유 모델로 전환 — rename 이 안전해지지만 도메인 구조 변경 +
  마이그레이션 + 같은 키워드를 사용자마다 중복 수집(외부 API 쿼터 증가)
- (C) `UserKeyword.displayName` 별칭 추가 — 표시만 바꾸고 수집어는 유지.
  "이름을 바꿨는데 수집 대상이 안 바뀐다"는 점이 목업 의도와 어긋난다

→ **(A) 확정 (태형님 회신 2026-08-17).** 이 서비스는 실사용상 단독 구독자가 지배적이라
목업과 동일하게 동작한다.

**(A) 확정에 따른 구현 규칙**

1. 새 `(이름, 지역)` 을 `registerKeyword` 와 같은 방식으로 find-or-create 하고 구독을 만든다.
   기존 구독의 `active` 상태를 새 구독에 **승계**한다(수정 모달의 토글 값이 최종값).
2. 기존 키워드의 **다른 구독자 유무로 분기**한다.
   - 단독 구독자: `news.keyword_id` 를 새 키워드로 **이관** → 기존 기사 유지(목업 약속 충족).
     이관 후 옛 키워드 행은 구독자 0 이므로 정리한다(단, `news` 를 이미 옮겼으므로 기사는 살아남는다).
   - 다중 구독자: 옛 키워드와 기사는 그대로 두고 구독만 해제한다.
     이 경우 기존 기사가 목록에서 빠지므로 **모달 문구를 조건부로** 바꾼다.
3. 새 `(이름, 지역)` 이 **이미 내가 구독 중인 키워드**면 병합이 된다 → 사전 검증으로 막거나
   "이미 등록된 키워드입니다" 안내. plan에서 확정.
4. 이름·지역이 **둘 다 그대로**면 활성 토글만 반영하고 재구독을 건너뛴다(불필요한 이관 방지).

`Keyword` 도메인 모델은 **불변을 유지**한다(변경 메서드를 추가하지 않는다) —
재구독 방식이라 rename 이 필요 없고, 공유 리소스 불변성이 오히려 안전장치다.

### 충돌 2 — 등록 모달의 `국내+해외` 는 백엔드에 없다

`Region` enum 은 `DOMESTIC`·`INTERNATIONAL` **2개뿐**이다.
그런데 등록 모달은 `국내 · 해외 · 국내+해외` **3개**를 제시한다(수정 모달은 2개로 일관).

선택지:
- (A) 키워드 2건 등록 — `국내+해외` 선택 시 같은 이름으로 국내·해외 두 건을 구독
- (B) `Region.BOTH` 추가 — 수집 시 국내·해외 포트를 모두 호출. enum·팩토리·검색 분기 변경
- **(C) 옵션 제거** — 수정 모달과 동일하게 2개로 맞춘다

→ **(C) 확정 (태형님 회신 2026-08-17).**
등록 모달의 `수집 범위` 를 `국내 · 해외` 2버튼으로 바꿔 수정 모달과 일관되게 한다.
`Region` enum·수집 포트 팩토리는 **손대지 않는다**.
목업 등록 모달의 3버튼 레이아웃(`flex:1` 균등 분할)은 2버튼으로 그대로 축소 적용한다.

## 추가 조사로 확인한 사실 (plan 설계에 직결)

### 사실 1 — ES 검색 결과에는 뉴스 id 가 없다

`NewsDocumentMapper.toDocument()` 가 ES `_id` 로 **`originalUrl`** 을 쓰고,
`NewsElasticsearchSearcher.toNews()` 는 `new News(null, …)` 로 **id 를 버린다**.
읽음/저장·유사 기사는 뉴스 식별자에 달리는 기능이라 그대로는 붙일 수 없다.

선택지:
- (a) `NewsDocument` 에 `newsId` 추가 + **전체 재색인** — 깔끔하지만 재색인 비용
- (b) 검색 결과 `originalUrl` 목록으로 DB 재조회(`findByOriginalUrlIn`) — 재색인 불필요, 쿼리 1방 추가.
  `original_url` 은 UNIQUE 라 안전하고, 언론사·읽음·저장을 **DB 한 곳에서** 같이 붙일 수 있다
- (c) 읽음/저장을 `originalUrl`(최대 500자) 키로 저장 — 인덱스 비효율

→ **(b) 권고.** plan에서 확정.

### 사실 2 — 검색어 없는 기본 화면은 ES 를 거칠 필요가 없다

목업 기본 상태("저장된 전체 뉴스 · 최신순")는 전문 검색이 아니다.
**검색어 없음 → DB 최신순 조회 / 검색어 있음 → ES 후 DB 보강** 2경로로 나누면
정렬이 안정적이고 상태 조인도 단순해진다.

### 사실 3 — 언론사는 수집 체인 전체를 타고 내려와야 한다

`NaverNewsItem` · `GNewsArticle` · `NewsApiArticle` 3종 DTO 모두 **언론사 필드를 매핑하지 않는다**.
GNews/NewsAPI 는 API 응답에 `source.name` 이 있으나 DTO 에서 버려지고,
Naver 는 응답 자체에 없어 `originallink` 도메인 파생이 유일하다.
전달 경로는 `…Item → NewsSearchResult → NewsResultDto → KeywordSearchContext → NewsSaveRequest → News → NewsEntity`
로 **7개 클래스 + Entity 컬럼**이 걸린다.

## 리스크

- `news-search`·`keywords` 두 partial과 `keyword.js`·`news.js`·`news-search.js` 세 컴포넌트를
  하나로 재편하는 작업이라 **프론트 변경 폭이 크다**(라우팅·partial 목록·cleanup 레지스트리까지).
- 빈 검색어 허용은 ES 쿼리를 `must(multi_match)` → 조건부로 바꾸는 변경이다.
  전체 매치 시 정렬 기준이 없으면 결과가 불안정해지므로 **최신순 정렬을 기본값으로 둬야 한다**.
- 키워드 스코프 필터는 "내 키워드가 아닌 keywordId"를 클라이언트가 넣을 수 있어
  #114 리뷰 H1과 같은 **소유권 검증**이 필요하다.
- 목업은 키워드 14개 / 기사 10건 고정 데이터다. 키워드 0개·100개, 기사 0건의 레이아웃이 정의돼
  있지 않아 빈 상태 규칙을 plan에서 정의해야 한다.
- 통계 API가 매 진입마다 전체 집계를 돌면 뉴스 테이블이 커질수록 느려진다. 인덱스 확인 필요.
- **범위 C는 Entity 신규 2~3개 + `NewsEntity` 컬럼 추가**다. CLAUDE.md Approval Gate 대상이라
  Phase 착수 전 개별 승인이 필요하다. 기존 데이터는 `source` 가 `null` 이라 표시 폴백이 필요하다.
- 유사 기사 클러스터링을 빼면 **같은 사건 기사가 스트림을 도배**하는 문제가 남는다.
  `ON CONFLICT (original_url)` 은 완전 동일 URL 만 막으므로, 여러 언론사가 쓴 같은 사건은 그대로 쌓인다.
  통합 화면은 v1 대비 기사를 더 많이 한 화면에 보여주므로 **체감이 더 커질 수 있다** → 후속 이슈 필요
- **키워드 수정은 공유 리소스를 건드린다**(충돌 1). 재구독 방식으로 가더라도
  `news.keyword_id` 이관 여부가 구독자 수에 따라 갈리므로, 단독/다중 두 경로를 모두 검증해야 한다.
- 벌크 삭제는 **되돌릴 수 없다**. 선택된 키워드가 여러 개일 때 기사까지 함께 사라지므로
  확인 모달에 대상 건수·기사 수를 명시해야 한다(목업 단건 모달을 다건용으로 확장 필요 —
  목업에 다건 확인 모달은 정의돼 있지 않다).
