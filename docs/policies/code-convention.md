# Code Convention

## 목적

이 문서는 저장소 전반에서 일관된 코드 구조와 리뷰 기준을 유지하기 위한 코드 컨벤션 정책이다.
구현과 리뷰는 이 문서를 기준으로 메서드 크기, 중첩 깊이, 책임 분리, 의존성 방향을 판단한다.

## 기본 원칙

- 작은 메서드를 기본값으로 유지한다.
- 중첩보다 guard clause와 조기 반환을 우선한다.
- 하나의 클래스와 메서드는 하나의 책임에 집중한다.
- 구체 구현보다 추상화와 역할 분리를 우선 검토한다.
- 규칙은 품질 향상을 위한 기본값이며, 예외는 제한적으로만 허용한다.

## 메서드 규칙

- 메서드는 가능한 한 5줄 이내로 작성한다.
- 6줄 이상이 필요하면 하나의 책임으로 설명 가능한지 먼저 검토한다.
- 10줄을 초과하는 메서드는 예외 사유 없이 작성하지 않는다.
- 예외가 필요한 경우에도 조건 분기, 데이터 변환, 외부 호출, 후처리를 한 메서드에 과도하게 섞지 않는다.

## 중첩 규칙

- 메서드 내부 중첩은 1단계를 기본 한도로 한다.
- 불가피한 경우에만 2단계까지 허용한다.
- 3단계 이상 중첩이 필요하면 메서드 분리, guard clause, 전략 분리, 상태 객체 도입을 먼저 검토한다.
- `if` 안에 `for`, `for` 안에 `if`처럼 흐름이 겹치면 조기 반환 또는 helper 메서드 추출을 우선한다.

## SOLID 적용 기준

### Single Responsibility Principle

- 클래스는 하나의 변경 이유만 갖도록 설계한다.
- 메서드는 한 가지 행위만 수행하도록 유지한다.
- 조회, 검증, 변환, 저장, 알림이 한 메서드에 같이 있으면 분리 대상을 검토한다.

### Open/Closed Principle

- 새 케이스 추가 시 기존 조건문을 계속 늘리기보다 역할 분리를 먼저 검토한다.
- 정책이 늘어나는 로직은 전략 객체, 정책 객체, enum 기반 행위 분리 등을 우선 고려한다.

### Liskov Substitution Principle

- 하위 구현은 상위 타입의 계약을 약화시키거나 예외적으로 깨지 않도록 한다.
- 동일 인터페이스 구현체가 호출자에게 서로 다른 전제조건을 강요하지 않도록 한다.

### Interface Segregation Principle

- 사용처 기준으로 작은 인터페이스를 유지한다.
- 구현체가 사용하지 않는 메서드를 억지로 구현하도록 만드는 큰 인터페이스를 피한다.

### Dependency Inversion Principle

- 상위 계층은 하위 구현 세부사항보다 추상화에 의존한다.
- application, domain 계층이 infrastructure 구체 구현 세부를 직접 알지 않도록 한다.

## 권장 리팩터링 방식

- guard clause 우선
- private helper 메서드 추출 우선
- 역할이 섞이면 클래스 분리 우선
- 조건 분기 확장 시 전략 또는 정책 객체 검토
- 변환 로직 반복 시 mapper 또는 factory 추출 검토

## 예외 정책

아래 경우에는 규칙을 제한적으로 완화할 수 있다.

- framework callback, mapper, converter, config 코드처럼 과도한 분리가 오히려 가독성을 해치는 경우
- transaction 경계, lock, retry, exception translation 등으로 한 흐름을 유지하는 편이 더 안전한 경우
- 성능상 과도한 메서드 분리가 불리한 hot path

예외를 적용하더라도 아래는 유지한다.

- 중첩 3단계 이상은 지양한다.
- 긴 메서드는 왜 분리하지 않았는지 설명 가능해야 한다.
- 예외는 기본 규칙을 무효화하지 않고 제한적으로만 허용한다.

## 리뷰 체크리스트

- 5줄 초과 메서드가 있는가
- 10줄 초과 메서드에 예외 사유가 필요한가
- 중첩 2단계를 초과한 메서드가 있는가
- 하나의 메서드 또는 클래스가 여러 책임을 동시에 가지는가
- 조건문 확장이 역할 분리 없이 누적되고 있는가
- 상위 계층이 하위 구현 상세에 직접 결합되어 있는가

## 위반 시 행동

- lightweight workflow에서는 즉시 구조 개선 가능 여부를 먼저 검토한다.
- documented workflow에서는 plan에 반영하거나 사용자 확인 후 진행한다.
- 규칙 위반이 의도된 예외라면 이유를 설명할 수 있어야 한다.
