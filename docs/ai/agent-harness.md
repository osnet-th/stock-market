# Agent Harness

이 파일은 Claude Code와 Codex 계열 에이전트가 이 저장소에서 작업할 때 공통으로 따르는 최상위 실행 하네스입니다. `AGENTS.md`와 `CLAUDE.md`는 이 문서를 필수 참조하는 래퍼 문서이며, 충돌 시 더 보수적인 규칙을 따른다.

상세 gate 문서는 이 하네스의 필수 구성이다. 작업 단계에 맞는 문서를 반드시 읽고 적용한다.
코드 맥락 이해가 필요한 Plan/Implementation 작업은 [briefing-harness.md](briefing-harness.md)의 실행 브리핑과 작업 단위 체크포인트를 함께 적용한다.

---

## Agent Contract

- 응답 시 항상 "태형님"이라고 호칭한다.
- 요청받지 않은 리팩토링, API 변경, 구조 변경을 하지 않는다.
- 코드 구현이나 수정은 승인된 `docs/plans/` plan 문서가 있을 때만 진행한다. 단, [Workflow Weight](#workflow-weight)의 lightweight 대상은 대화로 범위를 합의하고 태형님 승인을 받은 경우 plan 파일 없이 진행할 수 있다.
- issue 기반 Plan 또는 Implementation은 `/ce:plan` 전에 Harness Brainstorm 문서를 작성한다.
- brainstorm을 완료하면 plan 진입 전에 대응 GitHub 이슈가 있는지 확인한다. 비 이슈로 시작한 documented 작업에 대응 이슈가 없으면 brainstorm 내용을 바탕으로 이슈 등록을 태형님에게 제안하고, 등록되면 이슈 번호 기준 worktree로 전환해 issue 기반 흐름을 따른다([gates/github-issue-gate.md](gates/github-issue-gate.md)).
- issue worktree 작업의 현재 단계는 `{worktree}/.claude/issues/{이슈번호}/stage` 마커 파일로 관리한다(값: `brainstorm`, `plan`, `plan-approval`, `implement`, `review`, `explain`, `verify`, `pr`, `merge`). 단계 전환 시 이 파일을 즉시 갱신한다. UserPromptSubmit hook(`scripts/harness-stage-reminder.sh`)이 이 파일과 plan 상태로 매 턴 단계별 의무사항을 주입하며, 주입된 단계가 실제와 다르면 마커부터 갱신한다.
- issue 기반 Implementation은 GitHub 이슈 설명이 충분하더라도 반드시 `/ce:plan`을 거친다.
- issue 기반 Implementation은 active root plan 이후에도 직접 구현하지 않고 반드시 `/ce:work`로 구현을 시작한다.
- `/ce:work`의 구현 task 기준은 승인된 root `docs/plans/` plan의 작업 리스트와 `allowed_paths`/`blocked_paths`다.
- 리뷰 요청을 받으면 `/ce:review`를 수행한다. actionable issue 목록을 태형님에게 제시하고, 태형님이 선택한 이슈만 root plan 범위 안에서 수정한다. 비선택 이슈는 임의 수정하지 않고 보류로 기록한다.
- 리뷰와 선택 이슈 수정이 끝나면 `explain` 단계에서 구현 이해 확인 Gate를 수행한다. `check-implementation-explainer` 스킬의 설명 구조를 따라 현재 구현 흐름, 주요 변경 파일/컴포넌트, 계층별 구현과 역할, 구현 중 확정된 도메인 정책/조회 규칙, 요청에서 코드까지의 처리 흐름, 예외/권한/트랜잭션/외부 연동 영향, 유지보수 포인트, 잔여 위험, 그리고 root plan `## 요구사항 원장` 기준 요구사항 커버리지(REQ별 판정, 구현 위치, 충족 근거)를 프롬프트상으로 설명한다. 설명 후 커버리지 집계를 제시하고, `미충족`이 1건이라도 있으면 즉시 중단한다. `범위 제외`·`부분 충족`은 건별로 `수용` / `후속 이슈 생성` / `지금 구현 범위에 추가` 결정을 받은 경우에만 Gate 완료로 본다.
- 구현 이해 확인 Gate에 진입하면 [notion-guide.md](notion-guide.md)에 따라 구현 내용을 Implementation 페이지로 동기화하고, 이후 코드가 바뀌면 병합 전에 같은 페이지를 갱신한다. 검증 결과는 이 페이지에 쓰지 않는다.
- 구현 이해 확인 Gate가 끝나면 PR 여부를 묻기 전에 반드시 "검증은 어떤 걸로 실행할까요?"를 먼저 묻고, 태형님이 선택한 검증을 수행하거나 미실행 사유를 기록한다.
- 태형님이 실제 테스트를 선택하면 태형님 선택에 따라 `./gradlew test`(단위테스트) 또는 `bootRun` 기동 후 curl 실검증을 실행한다. 선택지를 물을 때 변경 규모 기준 권장안을 함께 제시한다.
- plan과 다른 구현이 필요하면 즉시 중단하고 plan을 업데이트한 뒤 재승인을 요청한다.
- 구조 변경, Entity 신규 작성, public API 변경 가능성이 있으면 구현 전에 명시적으로 승인받는다.
- Entity 신규/변경, Entity 관계 변경, DB table/column/index/constraint 변경 가능성이 있으면 구현 전에 DB Schema Review Gate를 수행하고 테이블 설계를 명시적으로 승인받는다.
- issue 기반 Plan 또는 Implementation에서 코드 맥락 이해가 필요한 경우 `briefing-harness.md`를 적용한다. plan 승인 전 현재 코드 기준 실행 브리핑과 plan-to-code 매핑 브리핑을 수행하고, 구현 중 합의된 큰 작업 단위가 끝나면 짧은 체크포인트 브리핑 후 태형님 확인을 받는다.
- 대상 4종(brainstorm/plan/리뷰 결과/구현 설명)을 [notion-guide.md](notion-guide.md)의 트리거에 따라 Notion에 동기화한다.
- `docs/ai/agent-harness.md`를 공통 하네스 정책의 단일 진입점으로 유지한다.
- `AGENTS.md`와 `CLAUDE.md`는 공통 하네스 정책을 직접 중복 작성하지 않고 이 문서를 참조한다.
- `AGENTS.md` 또는 `CLAUDE.md` 래퍼 문서 수정 시 상대 문서에도 동일한 참조 구조를 유지한다. 의도적으로 차이를 둘 경우 plan에 차이, 사유, 승인 여부를 명시한다.
- 코드 주석에는 GitHub 이슈 번호를 쓰지 않는다. 이슈 추적은 커밋 메시지, PR 설명, plan 문서에서만 한다.
- 커밋 메시지에는 AI/도구 작성자 정보를 포함하지 않는다. 금지 예: `Co-Authored-By`, `Generated by`, `Built with`, `Assisted by`.

## Work Classification

작업 시작 전 요청을 아래 중 하나로 분류한다.

- **Question**: 설명, 조사, 코드 읽기만 수행한다. 파일 수정 없음.
- **Plan**: `docs/plans/` 하위 plan 문서를 작성하거나 업데이트한다. 구현 없음.
- **Implementation**: 승인된 `docs/plans/` plan 문서에 따라 코드 또는 문서를 수정한다.
- **Bug Handling**: 문제를 발견하면 즉시 수정하지 않고 plan 문서에 분석과 해결 방안을 통합한다.
- **Review**: 버그, 회귀 위험, 아키텍처 위반, 누락된 검증을 우선적으로 찾는다.

분류가 불명확하면 더 위험한 분류를 선택한다. 예를 들어 코드 수정 가능성이 있으면 Plan 또는 Implementation으로 본다.

## Workflow Weight

작업 분류와 별개로 절차의 무게를 documented / lightweight 중 하나로 정한다. 기본은 documented다.

### documented workflow (기본)

아래 경우에는 Mandatory Workflow 전체를 적용하고 산출물을 파일로 남긴다.

- 비즈니스 로직 변경
- API, Entity, 구조 변경
- 요구사항 해석이 필요한 작업
- 영향 범위가 크거나 리스크가 높은 작업

### lightweight workflow

아래 경우에는 같은 단계 순서를 따르되 brainstorm/plan 산출물을 파일로 남기지 않을 수 있다.

- 오타 수정
- 명백한 컴파일 에러 수정
- 문서 수정
- 로직 의미 변경이 없는 국소적 수정

lightweight 규칙:

- current plan은 현재 대화에서 명시된 작업 범위와 단계로 갈음하고, 진행 전 태형님 승인을 받는다.
- 리뷰/검증/커밋/push 결과와 승인 여부는 대화에서 명시한다.
- stage 마커와 Notion 동기화는 생략할 수 있다.

### escalation

lightweight로 시작했더라도 아래 조건이 생기면 즉시 중단하고 documented workflow로 승격한다.

- 로직 의미 변경 필요
- 영향 범위 확대
- 요구사항 해석 필요
- 구조, API, Entity 변경 필요

## Mandatory Workflow

1. 요청 범위를 확인한다.
2. 관련 파일과 [ARCHITECTURE.md](../../ARCHITECTURE.md)를 읽는다.
3. 작업 유형을 분류한다.
4. 현재 작업에 필요한 gate 문서를 [Gate Routing](#gate-routing)에서 확인하고 읽는다.
5. issue 기반 작업 시작이면 [gates/github-issue-gate.md](gates/github-issue-gate.md)의 착수 절차(`scripts/start-issue-worktree.sh {이슈번호}`)로 worktree를 준비한다.
6. 구현/수정 작업이면 현재 브랜치와 worktree가 issue 작업 기준에 맞는지 확인한다.
7. 구현/수정 작업이면 승인된 `docs/plans/` plan 문서가 있는지 확인한다.
8. issue 기반 Plan 또는 Implementation이면 GitHub 이슈 상세 또는 태형님 요청을 입력으로 [brainstorm-harness.md](brainstorm-harness.md)의 Harness Brainstorm 문서를 먼저 작성한다.
9. issue 기반 Implementation이면 Harness Brainstorm 문서를 입력으로 어떤 경우에도 `/ce:plan`을 수행한다.
10. issue 기반이 아닌 구현/수정 작업에서 plan이 없거나 불충분하면 `docs/plans/`에 plan을 작성 또는 업데이트하고 승인을 기다린다.
11. issue 기반 Plan 또는 Implementation에서 코드 맥락 이해가 필요한 경우 [briefing-harness.md](briefing-harness.md)를 읽고, plan 승인 전 현재 코드 기준 실행 브리핑과 plan-to-code 매핑 브리핑을 수행한다.
12. Entity 또는 DB 스키마 변경 가능성이 있으면 [gates/planning-gate.md](gates/planning-gate.md)의 DB Schema Review Gate를 먼저 수행하고 태형님 승인을 받는다.
13. `/ce:plan` 이후 구현 시작 전 `/Users/thlee/Documents/personal/stock-market/scripts/validate-plan.sh {plan-file}`을 실행한다.
14. 구현/수정 작업 시작 전 `/Users/thlee/Documents/personal/stock-market/scripts/check-plan-conflicts.sh {이슈번호}`를 실행한다.
15. issue 기반 Implementation이면 `/ce:work`를 실행하고, 선택한 작업이 root plan 작업 리스트와 `allowed_paths`/`blocked_paths` 안인지 확인한다.
16. 승인된 plan 범위 안에서 한 번에 하나의 작업만 수행한다.
17. 구현 중 합의된 큰 작업 단위가 끝나면 [briefing-harness.md](briefing-harness.md)의 체크포인트 브리핑을 수행하고 태형님 확인 후 다음 큰 작업 단위로 진행한다.
18. 구현 중 새로운 문제나 plan 이탈이 필요하면 즉시 중단한다.
19. 리뷰 요청이면 `/ce:review`를 수행하고, actionable issue 목록을 태형님에게 제시한다. 태형님이 수정할 이슈를 선택하면 선택된 이슈만 plan 범위 안에서 수정한다. 비선택 이슈는 임의 수정하지 않고 보류로 기록한다. 리뷰 결론은 [notion-guide.md](notion-guide.md)에 따라 Review 페이지에 동기화한다.
20. 리뷰와 선택 이슈 수정이 끝나면 `explain` 단계에서 구현 이해 확인 Gate를 수행한다. 설명 구조와 커버리지·GAP 결정 규칙은 Agent Contract와 [gates/verification-gate.md](gates/verification-gate.md)를 따른다.
21. 구현 이해 확인 Gate에 진입하는 시점에 [notion-guide.md](notion-guide.md)에 따라 Implementation 페이지를 생성하고 구현 내용을 동기화한다. 검증 결과와 잔여 위험은 이 페이지에 싣지 않는다. Gate 진행 중 설명이 보완되면 같은 페이지를 갱신한다.
22. 구현 이해 확인 Gate가 끝나면 PR 여부를 묻기 전에 "검증은 어떤 걸로 실행할까요?"를 먼저 묻는다. 검증 후보에는 정적/문서 검증, `./gradlew test`, `bootRun` + curl 실검증, 미실행 사유 기록을 포함한다.
23. 선택한 검증 결과와 미실행 사유는 검증 증거 산출물에 남긴다.
24. 작업 완료 시 plan 체크리스트를 갱신한다.
25. issue 기반 Implementation 작업에서 완료 의사를 보이면 최종 응답 전에 [gates/git-pr-gate.md](gates/git-pr-gate.md)의 Implementation PR Gate를 수행한다.
26. PR 병합은 태형님 승인 후에만 수행하고, 병합 전 Gate 이후 코드 변경이 있었는지 확인해 있으면 [notion-guide.md](notion-guide.md)에 따라 Implementation 페이지를 갱신한다. 병합 후 [gates/git-pr-gate.md](gates/git-pr-gate.md)의 Final Cleanup Gate로 worktree 정리와 main 최신화를 수행한다.

## Stop Gates

아래 조건 중 하나라도 해당하면 즉시 중단하고 태형님에게 확인을 요청한다.

- 상세 중단 조건은 [stop-gates.md](stop-gates.md)를 필수 적용한다.
- 관련 gate 문서가 더 보수적인 조건을 제시하면 더 보수적인 규칙을 따른다.
- Stop Gate 예외도 [stop-gates.md](stop-gates.md)의 Exceptions 기준만 적용한다.
